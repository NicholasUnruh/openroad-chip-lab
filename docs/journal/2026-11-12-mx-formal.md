# Do the MX units compute what their formats define?

## Question

Each of the six block dot-product units (MXFP8 E4M3 and E5M2, MXFP6 E3M2 and E2M3, MXFP4 E2M1, NVFP4) passes about 2.1 million random vectors against a C++ reference. Random vectors rarely reach the corners: exact cancellation, a sticky bit 26 binades below the result, a zero block scale. Does a solver find any input on which a unit disagrees with its format's definition?

## Concept

`formal/mx_dot32_formal.v` restates each format from its definition. It decodes every code, forms the exact sum as one wide integer, and rounds it to nearest even. It shares no logic with the unit or the C++ reference. SymbiYosys hands both to the Bitwuzla SMT solver, which searches all inputs for a mismatch in the result or the flags. The unit's inputs are held for its seven-clock latency, so a depth-9 bounded check covers every input the case allows.

A free 32-lane dot product is too large for one query, so each element type is split into cases:

- **Products (MODE 0).** Two free lanes, the others signed zeros, free block scales. This checks decode, the products, the scale, rounding and the sign of an exact zero.
- **Alignment (MODE 1).** Two free lanes at unit scale, plus c with one fixed exponent per case. The sweep covers every exponent where c and the block sum interact, with 26 binades of margin each side.
- **Specials (MODE 2).** All 32 lanes, both scales and c free. Whenever the specification gives a NaN or an infinity, the unit must give it too, with the right flags.

## What I tried

- I ran `formal/run.sh` with a 1 h limit per case. E2M1, E3M2, E2M3 and NVFP4 ran every alignment exponent. E4M3 and E5M2 have wider exponent ranges and slower cases, so I checked every fourth exponent plus both ends (`STRIDE=4`).
- I fixed two flaws in the script. Without SymbiYosys on PATH, it read stale status files from an earlier run as passes. It now clears each case's directory and refuses to run without the tools.
- I reran the cases that hit the 1 h limit, and the E5M2 cases the first run did not reach, with a 4 h limit (`CASE_TIMEOUT=14400`).

## Output

| Element | Alignment cases | Products | Specials | Result file |
| --- | --- | --- | --- | --- |
| E2M1 | 60 of 60 pass | pass | pass | `e2m1_e3m2_e2m3.txt` |
| E3M2 | 68 of 68 pass | pass | pass | `e2m1_e3m2_e2m3.txt` |
| E2M3 | 64 of 64 pass | pass | pass | `e2m1_e3m2_e2m3.txt` |
| NVFP4 | 60 of 60 pass | **failed** before the fix, open after 4 h | pass | `nvfp4.txt`, `products_4h.txt` |
| E4M3 | 23 of 23 pass (every 4th) | open after 4 h | pass | `e4m3_e5m2_stride4.txt`, `products_4h.txt` |
| E5M2 | 30 of 30 pass (every 4th) | open after 4 h | pass | `e4m3_e5m2_stride4.txt`, `e5m2_rerun_4h.txt` |

All result files are in `results/formal/`. The solver time was about 56 h in total, much of it on the timed-out cases.

The NVFP4 products case failed in 3 seconds. Its counterexample had a zero E4M3 block scale and negative products. Every product in that block is then zero, and the exact sum is -0, but the unit returned +0. The unit's zero-result sign checked only the elements for zero, not the scales. The fix adds the scale test to the per-lane zero term (`rtl/mx_dot32_fp32.v`). It costs nothing: Yosys maps the fixed unit to 12,126 generic cells against 12,131 before, with the same flops, so the ASAP7 NVFP4 area stands. I reproduced the counterexample in the C++ reference, which returns 0x80000000. The random test now forces all-negative products and zeroed NVFP4 scales; it fails on the old RTL and passes on the fixed one.

## Result

- **One real bug, now fixed.** NVFP4 returned +0 for an exact -0 sum when a block scale was zero. Random testing never produced that combination; the solver found it in 3 seconds.
- **The small formats are checked completely.** For E2M1, E3M2 and E2M3, every case passes. The products, every alignment of c against the sum, and every special-value rule match the definitions for all inputs the cases allow.
- **The products cases with wide scales are open.** For E4M3, E5M2 and the fixed NVFP4, the solver neither found a mismatch nor finished in 4 hours. These cases join a free block scale to the widest products. They remain covered only by the 2.1 million random vectors per element type.
- **E4M3 and E5M2 alignment is sampled.** Every fourth exponent passes, so a fault confined to the skipped exponents is still possible.
